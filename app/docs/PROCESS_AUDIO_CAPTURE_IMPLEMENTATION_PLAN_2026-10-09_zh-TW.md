# 指定應用程式音訊擷取實作計劃

日期：2026-10-09  
狀態：已完成第一版原始碼實作及本機原生／ASR 流程驗證；完整發行包與使用者實際瀏覽器環境尚待驗收。詳見同目錄 `PROCESS_AUDIO_CAPTURE_IMPLEMENTATION_REPORT_2026-10-09_zh-TW.md`。

## 1. 目的與範圍

讓使用者選擇直播、播放器或通話所在的視窗，只將該應用程式的聲音送進既有翻譯流程，降低遊戲、通知及其他程式聲音的干擾。

UI 功能名稱使用「指定應用程式音訊」。視窗是選取入口，Windows Process Loopback API 的實際範圍是指定程序及其子程序，不能承諾同一瀏覽器中的單一視窗或分頁隔離。

第一版包含：

- 新增獨立音訊來源 `process_audio`，保留 URL、檔案、系統音訊與麥克風。
- 列出可選視窗，顯示程式名称及視窗標題，提供重新整理與來源測試。
- 每個任務只使用一種來源，開始後固定目標，更換目標須停止再開始。
- 目標程序退出時結束任務並提示重新選擇，不自動追蹤同名程序。
- 擷取失敗時明確回報，不自動回退至系統音訊或麥克風。
- 提供目標與擷取狀態；無聲不直接判定為故障。

第一版不包含多來源混音、單分頁保證、音源分離、自動追蹤前景視窗，以及執行中切換目標。本文不授權發布、推送或修改現有使用者設定。

## 2. 技術依據與限制

Microsoft 官方範例以 `ActivateAudioInterfaceAsync` 搭配 Process Loopback activation parameters，擷取指定 PID 的程序樹。範例標示最低 Windows build 20348；一般 Windows 10 22H2 build 19045 低於此門檻。

- 官方說明：https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/
- API 結構：https://learn.microsoft.com/en-us/windows/win32/api/audioclientactivationparams/ns-audioclientactivationparams-audioclient_process_loopback_params
- 官方程式碼：https://github.com/microsoft/Windows-classic-samples/tree/main/Samples/ApplicationLoopback

本機先前唯讀查詢回報 Windows build 26300，符合版本門檻，但尚未實測擷取。實作時仍需重新檢查 OS 版本與 API 初始化結果。

已知限制：

- 同一應用程式可共用音訊服務或子程序；選取一個視窗不代表只取得該視窗聲音。
- 選到視窗的 PID 不一定就是正確音訊程序樹根節點。瀏覽器等多程序程式需驗證目標解析策略，避免只抓到 renderer 而漏掉音訊。
- 目標沒有音訊 rendering stream 時可能收到靜音。
- 直播本身的人聲、BGM、音效仍混在一起；此功能不做分離。
- 相容性、設備切換、CPU 使用及新增延遲都需實測，不預設結果。

## 3. 架構

資料流：

`視窗選擇 → 目標驗證 → ProcessAudioGetter → 16 kHz PCM → 既有 VAD／ASR／字幕組句／翻譯／輸出`

採用小型原生 DLL 封裝 COM／WASAPI，由既有 Python 翻譯子程序延遲載入。先以獨立原型驗證 DLL 介面，再整合正式流程。DLL 位元架構需與載入它的 Python runtime 一致。

選擇 DLL 的理由是沿用既有 Python 子程序生命週期，避免新增 helper EXE 後，停止或強制結束 Python 時留下擷取程序。若原型證明必須使用 helper EXE，先修訂設計，明確加入 Windows Job Object、管線關閉及父程序退出清理；不得只依赖正常停止指令。

原生介面至少提供：啟動擷取、讀取有界音訊緩衝、查詢格式及狀態、停止、釋放資源。避免讓 native callback 阻塞於 Python／ASR 工作。停止操作須能喚醒等待讀取的執行緒。

`ProcessAudioGetter` 輸出契約：

- 16,000 Hz、單聲道、float32。
- 每幀 512 samples，保留未滿幀樣本。
- 重採樣維持連續狀態，處理靜音封包、不同封包長度及不連續旗標。
- 真正音訊中斷使用既有 `AUDIO_STREAM_GAP` 契約；正常靜音與中斷分開處理。
- 結束時送出既有 end-of-stream marker，正常停止或例外均釋放資源。
- 有界緩衝滿載時須回報丟失量與中斷，禁止悄悄累積無限音訊或無紀錄丟棄。

音訊來源替換不增加第二套 ASR／翻譯模型。CPU、CUDA、ROCm 發行包共用擷取實作，但各 runtime 的元件位置与載入方式均需驗證。

## 4. 目標識別與設定

新增獨立欄位保存來源及目標，不借用音效設備的 `device_index`。

建議任務目標結構包含 HWND、選定視窗 PID、程序建立時間、程式識別與解析後的擷取 PID。確切 API 欄位名稱於原型完成後確定。

視窗枚舉與目標解析由後端完成，前端不自行判定 PID。列表可隱藏無標題或無法識別的視窗，但不能因目前沒有聲音就排除目標。開始前重新檢查視窗、程序與建立時間，防止目標已退出或 PID 被重用。

不要無條件向父程序追溯，以免選到共用 launcher／桌面程序而擴大擷取範圍。無法可靠解析的多程序應用程式須清楚回報限制。

設定可保存上次來源與程式匹配資訊；PID／HWND 只作本次執行識別，重啟後不得直接沿用。重新匹配僅供預選，開始前仍驗證目前目標。

來源測試重用正式擷取 backend，短時間測試後確實釋放資源。回報：

1. 不支援／初始化失敗／目標不存在。
2. 已開啟，目前未偵測到聲音。
3. 已收到音訊，附音量資訊供確認。

測試不能只靠 PID 存在就宣告擷取成功，也不能以無聲宣告失敗。

目前多任務與常駐子程序有共用管理，需要檢查新來源是否暴露既有競用。第一版不擴充並行能力；若不能保證來源歸屬與停止隔離，至少阻擋相關衝突任務並提示，不能讓一個任務停止另一個目標。

## 6. 執行順序與階段門檻

### 階段 1：獨立原型

- 建置原生擷取元件與最小測試入口，不先接正式 UI。
- 驗證獨立播放器、常用瀏覽器與通話程式，識別視窗 PID／程序樹根節點的差異。
- 同時播放另一個程式的可辨識測試音，確認隔離效果。
- 驗證無聲讀取可停止、目標退出、反覆啟停與資源釋放。
- 保存短測音訊及環境／目標／音訊格式紀錄。

門檻：至少一個常用目標可穩定擷取並排除其他程式，瀏覽器範圍有明確紀錄，停止不會掛住。未通過時先處理原型，不直接整合 UI。

### 階段 2：接入既有流程

- 實作 PCM 適配與 `ProcessAudioGetter`。
- 同步一般啟動及常駐模型流程。
- 完成初始化失敗、無聲、目標退出、使用者停止與強制結束處理。
- 驗證目標結束時字幕與任務狀態正常收尾，重新開始不混入舊音訊。
- 檢查音訊中斷時既有 VAD／下游上下文契約，必要時補足來源狀態處理。

門檻：完成實際 ASR 與字幕輸出；反覆啟停後沒有殘留擷取資源或跨任務音訊。

### 階段 3：API 與 UI

- 新來源與目標欄位、視窗列表、測試、能力查詢及設定保存。
- 開始前重新驗證目標；執行中禁止切換目標。
- 顯示程序音訊範圍與瀏覽器限制。
- 區分靜音與故障，保持前後端狀態一致。
- 同步簡單模式與完整模式。

門檻：使用者能從選目標、測試、開始到停止完成流程，錯誤原因清楚；舊設定能載入。

### 階段 4：打包與驗收

- 驗證各發行 runtime 的元件部署、位元架構與延遲載入。
- GUI／runtime 版本不匹配時給明確提示。
- 使用隔離測試安裝，保留既有模型與設定。
- 完成新功能、既有四種來源與任務生命週期回歸。

門檻：實際打包版完成來源測試、ASR、字幕、停止及再次開始。未測的包須列為未驗證，不能由原始碼測試推定。

## 7. 驗證矩陣

| 情境 | 驗收要求 |
|---|---|
| 目標與另一個程式同時播放 | 取得目標，沒有另一程式的可辨識測試聲音 |
| 同瀏覽器多視窗／多分頁 | 紀錄實際範圍與穩定性，UI 提示符合結果，不宣稱單分頁隔離 |
| 暫停、長時間無聲、恢復 | 不忙迴圈或無限累積，恢復後正常辨識 |
| 目標關閉／重新開啟 | 舊任務收尾，PID 改變後要求重新選擇 |
| 視窗標題變化／最小化／失去焦點 | 檢查是否持續擷取與列表識別；異常須可解釋 |
| 耳機／輸出設備切換 | 驗證持續擷取或明確中斷，不悄悄換來源 |
| 不同取樣率／聲道與封包大小 | 樣本數、聲道轉換、重採樣連續性正確 |
| 無聲時停止、初始化途中停止 | 有限時間結束，無死鎖及殘留資源 |
| 連續反覆啟停 | 執行緒／handle／記憶體不持續成長 |
| 擷取緩衝過載 | 有界、記錄遺失與 gap，不無限累積延遲 |
| 常駐模型重用与來源切換 | 新任務目標與選擇一致，不沿用前次音訊 |
| 同時啟動與停止任務 | 不誤停別的目標；無法隔離時阻擋衝突 |
| 舊 runtime／缺少 DLL／不支援 OS | 明確阻擋新來源，既有來源仍可使用 |
| 四種既有來源 | 來源檢查、啟動、輸出與停止正常 |
| CPU／CUDA／ROCm 實際包 | 分別記錄元件載入、擷取、ASR、字幕與停止結果 |

自動化測試集中於來源映射、目標失效／PID 重用、runtime 能力缺失、PCM 轉換、停止喚醒、例外清理及兩條啟動路徑；UI 小調整不另寫鏡像測試。音訊隔離與實際 Windows API 相容性使用真實播放測試。

效能紀錄包含擷取封包時間、VAD 等待、ASR、翻譯、字幕顯示、CPU、記憶體與佇列積壓。與目前設備擷取比較時使用同一段音訊及相同模型設定，先量測再訂退化門檻，不承諾更快或更省資源。
